# Task-менеджер: roadmap

План работ по шагам. Требования (ТР-1…ТР-9) описаны в [REQUIREMENTS.md](REQUIREMENTS.md), инструменты — в [STACK.md](STACK.md).

Принцип порядка: сначала база и доступы, потом приложение выкладывается в интернет как можно раньше (этап 2), чтобы каждую следующую функцию сразу проверять на iPhone.

## Этап 0. Подготовка окружения

**Требования:** —

**Стек:** Node.js LTS, npm, Git, VS Code, Supabase CLI, Docker Desktop (необязательно), GitHub, Supabase, Vercel, Google Cloud Console.

**Подзадачи:**
1. Установить Node.js LTS, Git, VS Code с расширениями oxc, Prettier, Tailwind CSS IntelliSense.
2. Установить Supabase CLI. При желании разрабатывать с локальной базой — установить Docker Desktop.
3. Зарегистрироваться в GitHub, Supabase и Vercel (последние два — через GitHub).
4. Создать репозиторий на GitHub, склонировать его, положить туда `REQUIREMENTS.md`, `STACK.md`, `ROADMAP.md`.
5. Создать проект в Supabase, выбрать ближайший регион, сохранить URL проекта и публичный ключ (`sb_publishable_…`).
6. Создать проект в Google Cloud Console, настроить экран согласия OAuth (scopes: `email`, `profile`, `openid`), создать OAuth-клиент типа Web application.

**Готово, когда:** все аккаунты созданы, репозиторий склонирован, ключи Supabase и Google сохранены в надёжном месте (не в репозитории).

## Этап 1. Схема базы и правила доступа

**Требования:** ТР-1 (тип заметки), ТР-2 (столбец срочности), ТР-3 (название, описание), ТР-4 (пункты списка), ТР-5, ТР-6 (ярлыки), ТР-8 (архив), ТР-9 (участники и видимость).

**Стек:** Supabase Postgres, RLS, Supabase CLI (миграции), pgTAP.

**Подзадачи:**
1. Выполнить `supabase init` и `supabase link` к облачному проекту.
2. Создать миграцию с типами-перечислениями: `note_kind` (`permanent`, `temporary`) и `urgency` (`critical`, `urgent`, `not_urgent`, `no_deadline`).
3. Создать таблицы `profiles`, `notes`, `checklist_items`, `labels`, `note_labels`, `note_members` (поля — в [STACK.md](STACK.md#модель-данных)).
4. Добавить ограничения: `title` не пустой; уникальность ярлыка по (`owner_id`, `name`) и по (`owner_id`, `color`).
5. Написать триггер: при регистрации пользователя создаётся строка в `profiles`.
6. Написать триггер: при создании заметки создатель добавляется в `note_members` с ролью `owner`.
7. Написать триггер обновления `updated_at`.
8. Включить RLS на всех таблицах и написать политики:
   - `notes`, `checklist_items`, `note_labels` — доступ, если пользователь есть в `note_members` этой заметки;
   - `labels` — только владелец;
   - `note_members` — читать участников своих заметок, добавлять и удалять — только владелец заметки.
9. Применить миграции (`supabase db push`).
10. Написать pgTAP-тесты: пользователь Б не видит необщую заметку пользователя А; участник общей заметки видит и редактирует её.
11. Сгенерировать TypeScript-типы (`supabase gen types typescript`).

**Готово, когда:** миграции лежат в репозитории, тесты RLS проходят.

## Этап 2. Каркас приложения, вход и первый деплой

**Требования:** ТР-7 (доступ с разных устройств).

**Стек:** React, TypeScript, Vite, Tailwind CSS, React Router, TanStack Query, `@supabase/supabase-js`, Supabase Auth, Google OAuth, Vercel, oxlint, Prettier.

**Подзадачи:**
1. Создать проект: `npm create vite@latest` (шаблон React + TypeScript).
2. Подключить Tailwind CSS, задать тёмную тему и палитру.
3. Настроить oxlint и Prettier.
4. Подключить React Router: страницы «Доска», «Архив», «Ярлыки», «Вход».
5. Подключить TanStack Query.
6. Создать клиент Supabase, ключи вынести в `.env.local` (`VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`), добавить `.env.local` в `.gitignore`.
7. В Supabase включить провайдер Google, вставить Client ID и Secret из Google Cloud.
8. Сделать страницу входа «Войти через Google» и защиту маршрутов (без входа — редирект на вход).
9. Сделать шапку с аватаром и кнопкой «Выйти».
10. Подключить репозиторий к Vercel, задать переменные окружения.
11. Добавить адрес Vercel в Supabase (Site URL, Redirect URLs) и в Google Cloud (Authorized redirect URIs — адрес callback Supabase).
12. Проверить вход с ноутбука и с iPhone.

**Готово, когда:** по ссылке `*.vercel.app` можно войти через Google с ноутбука и с iPhone.

## Этап 3. Заметки: создание, редактирование, закреп

**Требования:** ТР-1 (постоянные и временные), ТР-3 (название и описание).

**Стек:** React, TypeScript, Tailwind CSS, TanStack Query, `@supabase/supabase-js`.

**Подзадачи:**
1. Написать слой доступа к данным: функции `listNotes`, `createNote`, `updateNote`, `deleteNote`.
2. Сделать компонент карточки заметки: название, описание, пустое описание не занимает места.
3. Сделать форму создания: название (обязательно), описание (необязательно), переключатель «Постоянная / Временная».
4. Сделать окно редактирования заметки по клику на карточку.
5. Сделать смену типа заметки у существующей.
6. Сделать блок «Закреплённые» вверху доски — только постоянные заметки.
7. Временно вывести временные заметки одним списком под закрепом (столбцы — на этапе 5).
8. Добавить оптимистичные обновления: изменение видно сразу, при ошибке откатывается.
9. Сделать удаление заметки с подтверждением.

**Готово, когда:** заметку без названия сохранить нельзя; постоянные заметки всегда в закрепе, временные — никогда.

## Этап 4. Списки-чеклисты

**Требования:** ТР-4.

**Стек:** React, TanStack Query, `@supabase/supabase-js`, dnd-kit (`@dnd-kit/sortable`).

**Подзадачи:**
1. Написать функции для `checklist_items`: добавить, изменить текст, отметить, удалить, изменить порядок.
2. В редакторе заметки сделать список пунктов: Enter создаёт новый пункт, Backspace в пустом пункте удаляет его.
3. Сделать чекбокс: нажатие зачёркивает пункт, повторное — возвращает.
4. Сделать блок «N выполнено» под невыполненными пунктами со сворачиванием.
5. На карточке показывать первые несколько пунктов и «…», как в Keep.
6. Сделать перестановку пунктов перетаскиванием.
7. Позицию хранить числом (`position`); новое значение при перестановке — среднее между соседями, чтобы не пересчитывать весь список.

**Готово, когда:** отметка пункта меняет только этот пункт, выполненные пункты уходят в свёрнутый блок.

## Этап 5. Доска срочности

**Требования:** ТР-2.

**Стек:** React, Tailwind CSS, dnd-kit (`@dnd-kit/core`, `@dnd-kit/sortable`), TanStack Query.

**Подзадачи:**
1. Сделать раскладку из 4 столбцов слева направо: Критично, Срочно, Не срочно, Без дедлайна.
2. Распределять временные заметки по полю `urgency`, внутри столбца — по `position`.
3. В форме создания добавить выбор столбца; по умолчанию — «Без дедлайна».
4. Сделать перетаскивание карточек между столбцами и внутри столбца (мышь и тач).
5. Добавить в меню карточки пункт «Переместить в…» — запасной вариант для телефона.
6. Сохранять `urgency` и `position` при каждом переносе (оптимистично).
7. Показывать счётчик задач в заголовке столбца.

**Готово, когда:** после перезагрузки страницы и на другом устройстве задача остаётся в новом столбце на своём месте.

## Этап 6. Ярлыки и цвета

**Требования:** ТР-5 (ярлыки и цвет карточки), ТР-6 (свои ярлыки).

**Стек:** React, Tailwind CSS, react-colorful, TanStack Query, `@supabase/supabase-js`.

**Подзадачи:**
1. Сделать страницу «Ярлыки»: список, создание, переименование, смена цвета, удаление.
2. Сделать выбор цвета: готовая палитра + произвольный цвет (react-colorful).
3. Запрещать занятый цвет и занятое название с понятным сообщением (ограничения уже есть в базе).
4. В редакторе заметки сделать выбор нескольких ярлыков и выбор основного.
5. Показывать ярлыки плашками на карточке.
6. Красить фон карточки цветом основного ярлыка; без ярлыка — цвет по умолчанию.
7. Подбирать цвет текста (светлый или тёмный) под фон карточки, чтобы текст читался.
8. Сделать фильтр доски по ярлыку.
9. Проверить: смена цвета ярлыка сразу перекрашивает все его заметки; удаление ярлыка снимает его с заметок, но не удаляет их.

**Готово, когда:** задачи с разными ярлыками на доске разного цвета.

## Этап 7. Архив

**Требования:** ТР-8.

**Стек:** React, React Router, TanStack Query, `@supabase/supabase-js`.

**Подзадачи:**
1. Заменить в редакторе кнопку «Удалить» на кнопку «В архив» со значком; добавить такую же на карточку. Заполняет `archived_at`, подтверждения не требует (действие обратимо).
2. Исключить архивные заметки с доски и из закрепа.
3. Сделать страницу «Архив» со списком заметок (новые сверху) и поиском по названию.
4. Сделать «Восстановить»: очищает `archived_at`, заметка возвращается в свой столбец.
5. Показывать уведомление «Заметка в архиве» с кнопкой «Отменить».
6. Сделать удаление навсегда из архива с подтверждением.

**Готово, когда:** заархивированная заметка пропадает с доски, видна в архиве и восстанавливается на прежнее место.

## Этап 8. Синхронизация в реальном времени

**Требования:** ТР-7 (синхронизация между устройствами), нефункциональное «изменения появляются за несколько секунд».

**Стек:** Supabase Realtime (`postgres_changes`), TanStack Query.

**Подзадачи:**
1. Включить Realtime для таблиц `notes`, `checklist_items`, `note_labels`, `labels`, `note_members`.
2. Подписаться на изменения после входа; при событии обновлять кэш TanStack Query.
3. Не применять повторно собственные изменения, которые уже показаны оптимистично.
4. При возвращении в приложение (iPhone выгружает фоновые вкладки) — переподключаться и перезагружать данные.
5. Показывать индикатор «нет связи», если соединение потеряно.
6. Проверить на двух устройствах одновременно: ноутбук и iPhone.

**Готово, когда:** заметка, добавленная с телефона, появляется на открытом ноутбуке без перезагрузки.

## Этап 9. Общие заметки

**Требования:** ТР-9 (совместный доступ, видимость, ярлыки на общей заметке).

**Стек:** Supabase Postgres (функции `security definer`), RLS, Realtime, React.

**Подзадачи:**
1. Написать SQL-функцию `share_note(note_id, email)`: находит пользователя по email и добавляет в `note_members`. Вызывать может только владелец. Второй пользователь должен хотя бы раз войти в приложение.
2. Написать функцию `unshare_note(note_id, user_id)` для прекращения доступа.
3. Сделать окно «Поделиться»: ввод email, список участников, кнопка «Закрыть доступ».
4. Показывать на карточке общей заметки аватары участников.
5. Написать SQL-функцию или представление, которое для второго участника сопоставляет ярлыки создателя со своими по названию.
6. Если у второго участника нет такого ярлыка — не показывать ярлык, красить карточку цветом по умолчанию и показать предложение «Создать ярлык „…“».
7. Если цвет ярлыка создателя у второго участника уже занят — при создании предложить выбрать другой цвет.
8. Добавить тесты RLS: необщие заметки (и постоянные, и временные) не видны другому пользователю.
9. Проверить совместную работу с девушкой: одновременные отметки пунктов, правка названия, архивация.

**Готово, когда:** пункт, отмеченный одним пользователем, сразу зачёркнут у второго; необщие заметки второй пользователь не видит.

## Этап 10. PWA и мобильная версия

**Требования:** ТР-7 (Windows, macOS, iPhone).

**Стек:** vite-plugin-pwa (Workbox), Tailwind CSS (адаптивность), Playwright (эмуляция iPhone).

**Подзадачи:**
1. Подключить vite-plugin-pwa: манифест (название, цвета темы, `display: standalone`), иконки, включая `apple-touch-icon`.
2. Настроить service worker: кэш статики, чтобы приложение открывалось быстро и без сети показывало последний экран.
3. Сделать мобильную раскладку доски: столбцы листаются вбок или переключаются вкладками.
4. Учесть особенности iPhone: отступы под «чёлку» и полосу жестов (`safe-area-inset`), крупные зоны нажатия, отсутствие масштабирования при фокусе на поле ввода.
5. Проверить, что перетаскивание не конфликтует с прокруткой на тач-экране (задержка перед захватом карточки).
6. Установить приложение на iPhone (Safari → «Поделиться» → «На экран Домой»), на Windows (Chrome/Edge) и на macOS (Chrome или Safari → «Добавить в Dock»).
7. Проверить вход через Google внутри установленного приложения на iPhone.

**Готово, когда:** приложение установлено на всех трёх платформах и открывается в своём окне без адресной строки.

## Этап 11. Бэкапы и CI

**Требования:** нефункциональные (сохранность данных).

**Стек:** GitHub Actions, `pg_dump` (Supabase CLI `supabase db dump`), Vitest, Playwright, oxlint.

**Подзадачи:**
1. Сделать workflow CI: на каждый push — lint, unit-тесты, сборка.
2. Добавить в CI прогон Playwright-тестов основных сценариев.
3. Сделать workflow бэкапа: раз в сутки по расписанию выгружать базу и сохранять как artifact (или в приватный репозиторий).
4. Хранить строку подключения к базе в GitHub Secrets.
5. Один раз проверить восстановление из бэкапа на отдельном тестовом проекте Supabase.
6. Записать в README, как включить проект Supabase после паузы.

**Готово, когда:** бэкап создаётся каждый день, и из него удалось восстановить базу.

## Этап 12. Тестирование и переход

**Требования:** все (проверка по критериям приёмки).

**Стек:** Playwright, ручное тестирование на iPhone, Windows, macOS.

**Подзадачи:**
1. Пройти критерии приёмки ТР-1…ТР-9 из [REQUIREMENTS.md](REQUIREMENTS.md) по списку.
2. Проверить сценарии на всех трёх платформах.
3. Неделю пользоваться приложением параллельно с Keep, записывать неудобства.
4. Исправить найденное.
5. Перейти на приложение полностью, Keep оставить только для чтения.

**Готово, когда:** все критерии приёмки выполнены и вы с девушкой пользуетесь приложением вместо Keep.
